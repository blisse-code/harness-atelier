# How it works

The short version is in the README. This page explains the thinking behind each part, so you can tailor a harness rather than just fill in a template. The full principles, with sources, are in [`skills/harness-atelier/references/principles.md`](../skills/harness-atelier/references/principles.md).

## Why a harness, not a better prompt

A prompt is one message. A harness is the environment every message lands in: what the AI reads first, what it is allowed to change, where it writes, how its output is checked, and how the setup improves after a mistake. The same model can do markedly better or worse work depending on that environment. A design team's work is ideal for a harness: the same pipeline (brief, research, design, review, delivery) repeats with the same kinds of input and output, and it mixes fixed steps with judgement.

## The five parts

**Rails** keep output inside what's allowed. A design system the AI can read (mirrored from Figma or code, never invented), user constraints written as rules ("users abandon setup when asked for details they don't have to hand"), and a confidentiality guard. Each component records what it must never become, and each pattern records its deliberate exceptions, so the AI doesn't "tidy up" a choice someone made on purpose.

**Memory** holds the truth between sessions and people. `CLAUDE.md` is kept short: a map of where things are, not a manual. Decisions are logged with who made them and why. Each session ends with a handover, and the next one starts by reading it back. If you find yourself re-explaining something to the AI, that is a bug in the memory, and the fix is a line in a file.

**Moves** is the workflow: your real stages, a skill for each recurring step, and hooks that put policy outside the model. At session start the hooks mirror the state back; before each write they guard confidentiality; at the end they refresh the dashboard and ask for a handover.

**Checks** come in two layers. Sensors are deterministic and cheap: a script that greps and reads tables. The gate is judgement: a separate evaluator agent works through a rubric built fresh each time from your scope, research constraints, rails and open feedback. The cheap layer runs first, so judgement is never spent on something a grep could catch. The evaluator is a different agent from the maker on purpose: makers grade their own work kindly.

**Loop** turns every miss into a permanent fix. A comment that recurs becomes a rule. A one-off UI that recurs becomes a component. A problem a grep could catch becomes a sensor. Each part of the harness is also a bet about what the AI can't do alone, so when the model changes, remove one part at a time and keep only those that still carry weight.

## Guides and sensors, per stage

Each stage in the map gets a **guide**, which steers before the work (a skill, a rule, a rail), and a **sensor**, which notices after (a check, a rubric line, a record). Guides alone never find out whether they worked. Sensors alone keep catching the same mistake. The map makes both visible before any file exists.

## Motion in this repo

The README diagrams are animated SVGs generated by `docs/visuals/build_visuals.py`. The rules:

- **One idea per animation**: a cycle (the five parts), a progression (the phases), a filter (the check ladder), a loop (miss to fix).
- **Slow loops** of 9 to 14 seconds, so the page never feels busy.
- **CSS only**, so `prefers-reduced-motion: reduce` stops all of it. With motion off, each diagram shows its complete final state. Motion adds emphasis, never content.
- **Light and dark** palettes that follow your GitHub theme.

The generated dashboard follows the same rules. Sections fade in, numbers count up and stage bars fill. Nothing moves when the viewer has asked for reduced motion, and no information depends on motion.
